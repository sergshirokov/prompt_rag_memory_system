# Замечание: отказ от хранения RAG-контекста в истории

## Контекст

В текущей реализации проекта история диалога хранит только:
- исходный вопрос пользователя;
- финальный ответ ассистента.

Служебный RAG-контекст (retrieved chunks, собранный prompt с контекстом, служебные источники для текущего запроса) в историю не сохраняется.

## Что это означает на практике

- Для каждого нового сообщения retrieval выполняется заново только по текущей формулировке вопроса.
- История Q/A передается в LLM на этапе генерации ответа, но не участвует напрямую в формировании embedding-запроса к векторному поиску.
- Из-за этого возможен разрыв: генерация учитывает диалог, а retrieval может быть слабым при анафоре ("этот", "тот", "как у предыдущего").

## Пример риска (UX-сценарий)

1. Пользователь спрашивает цену конкретной модели ноутбука (модель явно указана).
2. Бот корректно находит релевантные chunks и отвечает.
3. Следом пользователь пишет: "Какие у него характеристики?" без повторного указания модели.
4. Текущий retrieval строится по новому короткому вопросу и может не найти нужные chunks именно по этой модели.
5. Итог: ответ может быть частично верным, неточным или с риском догадки.

## Вывод по архитектуре

Решение "не хранить RAG-контекст в истории" само по себе допустимо и часто применяется.
Проблема возникает, если одновременно не реализован history-aware retrieval.

## Рекомендуемая практика (кратко)

- Не тащить все прошлые chunks в каждый новый запрос.
- Хранить короткое структурированное состояние диалога (сущности/ограничения), а не сырой RAG-контекст.
- Перед retrieval делать переформулировку вопроса в самодостаточный вид с учетом истории (query rewrite).
- При неоднозначности задавать уточняющий вопрос вместо догадки.

## Формулировка замечания

Текущая реализация осознанно не сохраняет RAG-контекст в истории, что снижает шум и токен-бюджет, но без history-aware retrieval создает риск потери релевантности в многошаговых диалогах с отсылками к предыдущим сущностям.
